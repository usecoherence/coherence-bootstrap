M1 migration execution decision

Decision:
- Buy generic migration mechanics with refinery.
- Build Coherence-specific ownership conventions and module layout.

Why:
- We need reliable ordered migration execution and applied-version tracking now.
- Reimplementing migration tracking in M1 would be unnecessary build risk.
- `coherence-core-db` still owns lifecycle orchestration and module boundaries.

What Coherence owns:
- migration layout under sql/modules/<module>/migrations
- ownership metadata in migration files
- product commands (`migrate`, `doctor`, smoke checks)
- policy and review boundaries

What refinery owns:
- ordered execution of versioned migration files
- migration history table and applied-version tracking
- migration mechanics and checksums

Current M1 scope:
- spec module migration files only
- no custom migration runner
- no rollback framework
- no dependency solver
